## 1. Что было сделано (краткая история)

До 30 мая 2026 проект `p2p-system` существовал только локально на ПК Acer Aspire XC600. Трекер собирал данные с Binance и Bybit, но только когда компьютер был включён. Из-за отключений света, рабочих смен и других причин трекер часто простаивал — данные собирались с дырами.

30 мая был куплен VPS у HostZealot (Варшава, Ubuntu 24.04). Туда переехали бэкенд (FastAPI) и трекер (APScheduler). С этого момента сбор данных идёт **круглосуточно и не зависит от состояния твоего ПК**.

Параллельно перед переездом были закрыты блокеры из code review:
- Защита write-эндпоинтов API-ключом (`X-Api-Key` header)
- CORS через переменные окружения
- Индексы в БД на ключевых таблицах
- Исправлен расчёт реализованного P&L
- Исправлен залипающий тултип в чарте
- Retry с дифференциацией HTTP-ошибок (429 / 5xx / network / 4xx)
- Создан `requirements_lock.txt` для повторяемых установок
- Созданы systemd unit-файлы

После переезда настроена новая локальная среда: ярлык `P2P` на рабочем столе, панель разработки с кнопками, скрипты для основных операций.

### 2.2. Поток данных

1. **Сбор:** `p2p-tracker` на VPS делает HTTP-запросы к Binance/Bybit P2P API каждые 60 секунд, парсит ответы и записывает снапшоты в `data/p2p.db`.
2. **Отдача:** `p2p-api` (FastAPI) читает из той же БД и отдаёт данные по REST.
3. **Фронт:** локальный Vite на твоём ПК (`localhost:5173`) делает запросы к VPS API. GET-запросы открытые, POST/DELETE требуют `X-Api-Key` header.

## 4. Рабочий процесс — ежедневный workflow

### 4.1. Утром / придя с работы

1. Включаешь ПК
2. Двойной клик на ярлык **P2P** на рабочем столе
3. Открывается:
   - Окно "P2P Vite" — фронт собирается, через 5-10 секунд готов
   - Окно "P2P Panel" — Python HTTP-сервер для отдачи `panel.html` на порту 9999
   - Вкладка браузера с фронтом (`http://localhost:5173`)
   - Вкладка браузера с панелью (`http://localhost:9999/panel.html`)
4. На фронте смотришь графики, добавляешь сделки. Данные приходят с VPS.

### 4.2. Перед выключением ПК

Просто выключаешь компьютер. Никакие сервисы останавливать не нужно — основные сервисы крутятся в Варшаве. Окна Vite и Panel закроются сами, на VPS это никак не повлияет.

### 4.3. Если нужно посмотреть что на сервере

Открой `panel.html` (или используй вкладку панели). Там есть кнопки и команды:
- **SSH → VPS** — копирует команду подключения, вставь в PowerShell
- **Команды для VPS** — готовые команды для копирования: статус сервисов, логи трекера, логи API, рестарт, SQL-запросы к БД

## 5. Рабочий процесс — разработка

### 5.1. Принцип "две среды"

Чтобы случайно не сломать production, у тебя есть **изолированная локальная среда**.

**Локальная среда (на ПК):**
- Локальный FastAPI на `http://localhost:8000`
- Локальный фронт на `http://localhost:5173` ходит на локальный API
- Локальная SQLite БД (`data/p2p.db` на твоём ПК)
- Трекер локально **не запускается** — данных в локальной БД мало или нет
- Ломай здесь что угодно — VPS никак не пострадает

**Production среда (на VPS):**
- FastAPI на `http://185.223.57.171:8000`
- Трекер постоянно собирает данные в `data/p2p.db` на сервере
- Эту среду напрямую руками **не трогаешь**, только через `deploy.bat`

### 5.2. Переключение между средами

На панели разработки две большие кнопки:

- **Dev Local** → запускает локальный API + Vite, который смотрит на локальный API. Создаёт `frontend/.env.local` с `VITE_API_URL=http://localhost:8000`.
- **View Production** → запускает только Vite, который смотрит на VPS. Удаляет `frontend/.env.local`, тогда Vite использует `frontend/.env` где production-URL.

Переключение — это просто запуск нужного `.bat`. Под капотом меняется один файл.

### 5.3. Цикл разработки новой фичи

Допустим хочешь добавить новый эндпоинт или поправить фронт:

1. **Запускаешь `Dev Local`** — работаешь на локальной среде
2. **Меняешь код** в Claude Code или редакторе
3. **Тестируешь локально** — Vite с hot-reload, FastAPI с `--reload`
4. **Закоммитил изменения:** `git add . && git commit -m "..."` (через Claude Code или вручную)
5. **`Deploy → VPS`** на панели — код летит на сервер автоматически
6. **Проверяешь** что на VPS всё ок — кнопка View Production или SSH

### 5.4. Если нужны реальные данные для тестов

На локальной БД данных может не быть. Чтобы поиграться с реальными:

- Кнопка **Скачать БД** на панели → запустит `pull_db_from_vps.bat`
- Скопирует production-БД с VPS в `data/p2p_prod_2026-05-31_1530.db` (с timestamp)
- **НЕ перезаписывает** твою рабочую `data/p2p.db` — это отдельный файл для анализа
- Можешь временно подменить локальную БД на эту копию, если нужно

## 7. Описание systemd-сервисов на VPS

### 7.1. p2p-tracker.service

**Расположение на VPS:** `/etc/systemd/system/p2p-tracker.service`
**Исходник в репо:** `deploy/systemd/p2p-tracker.service`

Запускает `scripts/run_tracker.py` от имени пользователя `p2p`. При падении автоматически перезапускается через 10 секунд (`Restart=always`).

Команды управления:
```bash
systemctl status p2p-tracker          # текущий статус
systemctl restart p2p-tracker         # перезапуск
systemctl stop p2p-tracker            # остановить
systemctl start p2p-tracker           # запустить
journalctl -u p2p-tracker -f          # смотреть логи в реальном времени
journalctl -u p2p-tracker -n 100      # последние 100 строк логов
```

### 7.2. p2p-api.service

**Расположение:** `/etc/systemd/system/p2p-api.service`
**Исходник:** `deploy/systemd/p2p-api.service`

Запускает `uvicorn api.main:app --host 0.0.0.0 --port 8000`. Сейчас слушает на всех интерфейсах (доступен снаружи) — это для текущего MVP. В будущем при добавлении Cloudflare Tunnel можно переключить на `127.0.0.1` (альтернативная команда есть в файле, закомментирована).

Команды управления — те же что у трекера, замени `p2p-tracker` на `p2p-api`.

## 9. Известные нюансы и подводные камни

### 9.1. CORS на сервере

Сейчас на VPS в `config/.env` стоит `CORS_ORIGINS=*` (разрешены любые источники). Это упрощение, которое сделал автодеплой при первой настройке. Безопаснее ограничить конкретными origins (например `http://localhost:5173,http://127.0.0.1:5173`), но **не критично**: API-key защищает write-эндпоинты, а GET-запросы возвращают публичные данные о рынке.

Когда захочешь усилить — отредактируй `/opt/p2p-system/config/.env` через SSH, потом `systemctl restart p2p-api`.

### 9.2. API_KEY засветился в чате

В процессе настройки production API_KEY несколько раз попадал в наш диалог. Ты сознательно решил не ротировать его сейчас (никаких реальных денег и приватных данных в проекте нет — только котировки с публичных бирж). Когда соберёшься делать аудит безопасности — сгенерируй новый ключ и обнови в трёх местах:
1. `/opt/p2p-system/config/.env` на VPS
2. `frontend/.env` на ПК
3. `panel.html` на ПК
Потом `systemctl restart p2p-api` на VPS и `dev_local.bat` рестарт.

### 9.3. Vite иногда плавает на порт 5174

Если запустить два Vite одновременно, второй возьмёт порт 5174. Открывай в браузере `localhost:5173` или `5174` в зависимости от того, какое окно последнее живо. Перед запуском убедись что старый Vite закрыт (Ctrl+C в его окне или просто закрыть окно).

### 9.4. Provider SSH keys на VPS

В `/root/.ssh/authorized_keys` на VPS лежат SSH-ключи сотрудников HostZealot (Emergency Remote Hands). Это легитимная функция — провайдер может зайти на сервер чтобы помочь при критических проблемах. Если когда-то решишь это убрать — открой тикет в support и попроси удалить, либо удали руками (но тогда лишишься Emergency Hands поддержки).

### 9.5. Локальный трекер дублирует production

Если случайно запустишь старый `start_all_OLD_LOCAL.bat.bak` (или похожий) — на ПК поднимется второй трекер, который начнёт писать в **локальную БД**. Это не сломает production, но забьёт твой диск и создаст путаницу. Если такое случилось — `Ctrl+C` в окне трекера, окно закрыть.

### 9.6. БД не мигрирует автоматически

`deploy.bat` обновляет код и зависимости, но **не делает миграций БД**. Alembic в проекте не используется. Новые таблицы `create_all` создаёт сам при старте приложения, но новые колонки в существующих таблицах — нет. Нужен ручной `ALTER TABLE` через SSH.

**Пример (выполнено 6 июня 2026 — миграция торговых сессий):**
```bash
# 1. Бэкап — обязателен перед любым ALTER
cp /opt/p2p-system/data/p2p.db /opt/p2p-system/data/p2p_backup_pre_sessions.db

# 2. Задеплоить код → create_all создаёт новую таблицу sessions автоматически
#    (запуск init_db: python -m scripts.init_db)

# 3. Добавить колонку в существующую таблицу (сервис нужно остановить)
systemctl stop p2p-api
sqlite3 /opt/p2p-system/data/p2p.db \
  "ALTER TABLE trades ADD COLUMN session_id INTEGER REFERENCES sessions(id);"
systemctl start p2p-api
```

Бэкапы на VPS: `p2p_backup_pre_sessions.db` и `p2p_backup_before_session_cleanup.db` (оба от 6 июня 2026).

#### ✅ 1B: Бэкенд (8506a3a)
`api/routers/sessions.py` — 5 эндпоинтов:
- `POST /api/sessions/start` — старт, проверка на уже активную (409), защита `require_api_key`
- `POST /api/sessions/{id}/close` — закрытие: берёт SELL-курс из `get_orders` **самостоятельно** (фронт курс не передаёт — защита от подделки P&L). Фиксирует цифры навсегда. Если курс недоступен → **503**, сессия остаётся `active`
- `GET /api/sessions` — список, сортировка по number DESC, счётчик сделок
- `GET /api/sessions/active` — активная или `null`
- `GET /api/sessions/{id}` — детали + список сделок (SessionDetail с trades[])

Новые сделки (POST /api/trades) автоматически получают `session_id` активной сессии.

**Формула P&L (проверена, зафиксирована):**
```
avg_buy_price  = total_uah_spent / total_usdt_bought     # средневзвешенная
realized_uah   = uah_received − usdt_sold × avg_buy_price
unrealized_uah = usdt_remaining × (current_sell_price − avg_buy_price)
total_pnl      = realized + unrealized                   # фиксируется при закрытии навсегда
```
⚠ Не путать с `TradeStats` (там другой расчёт — не использовать для сессий).
Курс закрытия берёт бэкенд сам — фронт его не передаёт (защита от подделки P&L).

## 12. Куда обращаться при проблемах

### Сервер недоступен (не открывается фронт)

1. Открой `ssh_to_vps.bat`
2. `systemctl status p2p-tracker p2p-api`
3. Если что-то не `active (running)` → `systemctl restart p2p-tracker p2p-api`
4. Если ребут не помог → `journalctl -u p2p-api -n 100` посмотреть ошибки

### Трекер не собирает данные

1. SSH на VPS
2. `journalctl -u p2p-tracker -f` — смотри живые логи
3. Если ошибки про Binance/Bybit API → возможно у бирж проблемы или rate limit, подожди
4. Если ошибки про БД → проверь место на диске `df -h`

### Фронт не открывается локально

1. Проверь что Vite реально запущен — должно быть окно "P2P Vite"
2. Открой `localhost:5173` (или 5174 если 5173 был занят)
3. Если Vite упал — закрой все окна, запусти заново через ярлык P2P

### Деплой упал

1. Открой `ssh_to_vps.bat`
2. `cd /opt/p2p-system && git status` — посмотри состояние репо
3. Если конфликты — разрулить вручную через git
4. Перезапусти `deploy.bat` после фикса

**Известная проблема `safe.directory` (6 июня 2026):** после смены владельца файлов `.git/` на VPS `git pull` завершается с `fatal: detected dubious ownership`. Лечится разово:
```bash
git config --global --add safe.directory /opt/p2p-system
```
Затем деплой продолжить вручную через SSH: `git pull origin main && systemctl restart p2p-api`.

### Что-то совсем непонятное

Заходи в Claude Code или новый чат с Claude в браузере, описывай проблему, давай этот документ как контекст. Большинство проблем решаемы за 10-15 минут.
